# 音声回答の発音前再判定

## mainから継承する方針

即時応答はBotへの明示的な呼びかけ・直接質問に限定する。通常会話は定期観測に任せる。タスク作成には既存の権限確認と確定した委任の根拠を必要とし、単なる提案・未決定の相談を実行許可にしない。受付は既存のタスク／議論スレッドに残す。

この変更は、上記の入口条件とタスク権限を広げず、音声を出す直前の判断を追加する。

## 通常STT/TTS経路

1. 入口を通った発言に対し、音声要否を `reply / pass / unknown` で判定する。`pass` はタスクの実行禁止を意味しない。タスクの観測・認可は従来の経路で独立して行う。
2. 返信が必要なら既存の回答／調査処理で内容を作成する。回答のテキスト投稿と音声再生は独立する。
3. TTS生成後、未確定の発話・文字起こし・入力処理がなくなるまで待つ。元の質問、用意した回答、最新の会話から `keep / cancel / unknown` を判定する。解決・撤回の取消には元の質問より後のユーザ発言IDを要求する。自己生成した回答は解決の証拠にしない。
4. 判定中に会話が変わった場合は古い判定を捨てる。無音待ちの終了後にも文脈版を同期確認し、再生開始までに非同期処理を挟まない。版が変わっていれば再判定へ戻る。
5. 再生中に誰かが話し始めたら停止する。STT対象者の許可リスト外の参加者にも話す順番を譲る。停止した音声の残りは自動再開しない。タスクは停止しない。

正規化した同一質問の候補は最新のものを優先する。新しい回答の後に古い生成が完了しても古い候補を再生しない。意味が似ているだけの質問を自動的に同一視する処理は含めない。

候補の有効期間は作成から90秒。`unknown`、不正なモデル出力、API失敗、期限切れでは音声を出さず、投稿済みのテキストを残す。無音待ちが長い場合も期限を超えた候補は再生しない。

音声にする通知は回答・質問された作業状況・文脈に関連するタスク結果。通常の受付・制御通知は音声にしない。タスク結果は既にタスクスレッドへ投稿済みでも再判定の対象にでき、同じ実行版はセッション中に一度だけ音声候補にする。取り消した結果を自動で再通知しない。

## Live経路の範囲

Liveはストリーミング音声を直接生成する別経路。受領・開始の宣言をしないこと、後続で解決した質問を繰り返さないことを発言方針に追加する。参加者の発話開始で出力をクリアし、発話中の受信音声は従来どおり破棄する。STT対象者以外の発話開始もこの停止に通知する。

上記の `SpeechTicket` による厳密な文脈版チェックは通常TTSに適用する。Liveの音声イベントには通常接続で回答単位のIDや完了境界がないため、Live全体の意味的取消を同じ仕組みで保証したとは扱わない。

## モジュールと評価

- `src/engine/reply/policy.mjs`: 音声要否・再判定のプロンプトと取消根拠の検証。
- `src/engine/reply/speech-ticket.mjs`: 文脈版、STT待機、期限、候補の失効。音声APIに依存せず単体テスト可能。
- `src/providers/openai-audio.mjs`: ツールなし・保存なしの構造化判定。既存の `quickReplyModel` 設定を使用し、モデルは変更しない。
- `src/engine/output/speech.mjs` / Discord transport: 非同期の再確認と、同期的な再生開始条件の橋渡し。

既存のアノテーションは音声要否の評価用として扱う。取消は初期返信が必要だったケースで別に評価する。既存のオフライン評価と、本番モデル・入力形式・入口条件が完全に同じではないため、その数値を本番精度と表現しない。

次の評価では発話開始／終了・STT確定・モデル判定・再生開始／停止の時刻を記録して、実際の遅延で利用可能な文脈だけをリプレイする。重複の意味判定、Liveの厳密な取消、実機での停止遅延、追加API呼び出しの応答遅延は別の検証対象とする。

検証コマンド: `npm run verify`。会話本文・アノテーション・個別のモデル予測はPRに含めない。
