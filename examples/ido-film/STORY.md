# IDOエンジンの発表・撮影台本

主張は「会議の文脈で試作し、触った感想を同じCodexタスクへ返す」。
会議が終わるときに、議事録と宿題に加えて、**触って判断できる試作がある**ことを見せます。
T118の2分動画へ差し込む素材です。呼称は「IDOエンジン」に揃え、音声では「イドエンジン」と読みます。

## 117秒の発表ストーリー

台詞の正本は `content-t118.json` の `voice` です。T118と同じ6場面・同じIDを保っています。

| 尺 | 見せるもの | 台詞の役割 |
| --- | --- | --- |
| 0–12秒 | ワープと連続移動が同時に動く | 「どちらがいい？」と、観客自身の判断を誘う |
| 12–28秒 | 会議の短い会話 | チームでの再説明・持ち帰りが課題であると伝える |
| 28–53秒 | 元発言の実画面と、生成された比較試作 | 会話調整とCodexの作業をつなぐ仕組みを説明する |
| 53–82秒 | 感想、実際の修正履歴、修正到着、前後比較 | 会話から体験へ、体験から修正へ戻る一周を見せる |
| 82–102秒 | 当日のプレビュー・修正依頼・前後比較 | 開発でCodexをどう使ったかを具体化する |
| 102–117秒 | 対象チームと展開先、最後の一文 | 次の制作会議でも使う理由を残す |

生成の待ち時間にはジャンプカットを使います。初回生成約4分44秒、追加修正約1分32秒は、この準備済みデモの各1回の記録です。「瞬時に完成」「一般にこの時間で作れる」とは言いません。

## 撮影用56秒の素材

`ido-film-reel.mp4` は1920×1080、無音の差し込み素材です。
会話と進行表示は台本で再生します。試作の移動操作は実際に動き、APIの呼び出しはありません。
画面上にも「撮影用画面・生成済みの試作」と表示します。

| 素材内の位置 | 場面 | T118での使い方 |
| --- | --- | --- |
| 00:00–00:08 | 二方式を同時に操作 | 冒頭に使用。タイトルを長く説明する前に動きを見せる |
| 00:08–00:16 | 「同じコースで、両方を試したい」 | 課題からユースケースへの橋渡し |
| 00:16–00:28 | 会議の文脈と生成された試作 | 議事録の実画面からカットをつなぐ |
| 00:28–00:40 | 「速すぎる。半分にして」 | 感想を返す場面。直後に実システムの修正履歴を置く |
| 00:40–00:50 | 速度1.0と0.5を同じ入力で比較 | 手触りの違いを見せる補助映像。実際の過去版比較としては扱わない |
| 00:50–00:56 | 「会議の出口に、触って判断できるものを」 | 末尾の言葉と合わせる |

速度比較は**同一の生成済み試作のパラメータ切替**です。T118が収録した同一タスクの修正履歴・修正到着・実際の版比較を最低10秒残し、因果関係の証拠にします。
収録画面を演出画面で全面的に置き換えません。

### 操作を自分で収録する場合

`http://127.0.0.1:4348/ido-film/` を開きます。
「56秒を再生」で一周、「場面」で任意の場面へ移り、「両方を前へ」で二方式を同時に試せます。
全画面でも撮影できます。Spaceは再生・停止、左右キーは場面切替です。
`?capture=1` は下部の撮影操作を隠すための指定です。

1. 最初に二つの移動方式を1回ずつ前へ動かします。視線を試作へ向けるため、冒頭3秒は話さなくても成立します。
2. 会議の発言を出し、生成済みの試作へカットをつなぎます。実システムで待機した部分には「待機を短縮」を表示します。
3. 「速すぎる」で修正依頼へ寄り、届いた版を開く実画面を見せます。顔出しや役者の芝居は必須ではありません。
4. 速度比較を一度だけ見せ、最後の一文へ進みます。目標を集めるゲームの説明で尺を使い切らないようにします。

## 短い口頭版

> ワープと連続移動、どちらがいいか。会議で迷ったら、その場で試したい。IDOエンジンは会議の文脈を受けてCodexへ作業を渡し、触って比べる試作につなぎます。速すぎると感じたら、同じタスクへ伝えて直す。会議の出口に、触って判断できるものを残すエンジンです。

## 発表での言い方

| 元の狙い | 発表に使う言葉 | 根拠・範囲 |
| --- | --- | --- |
| 会議をしているだけで動くものができる | 会議の会話から、試作を進める | 自動開始・手動依頼の仕組み。今回の映像は準備済みデモ |
| コンテキスト共有のコストが無い | 会議の内容をAIへ説明し直す往復を減らしたい | 議事録と原発言を検索できる。説明コストの定量測定はない |
| すぐに実現可能性が分かる | 議論中に、調査や試作を進める | 調査タスクの種類・割り当ては実装。映像の実演は試作・修正に絞る |
| リアルタイムに修正する | 会議を続けながら、同じタスクへ修正を返す | 即時完成とは言わず、待機を短縮したことを画面で示す |
| Slack・VRChatからも使える | 次はSlackやVRChat、画面共有の認識へ広げたい | 今回は将来構想。実装済み入口として説明するのはDiscordとブラウザ |
| VRで体験を担保できる | ブラウザの試作で、移動の違いを比べる | VR実機の快適性・酔いは別途検証が必要 |
| 多くの企業のボトルネック | 私たちが減らしたい、チームの再説明と持ち帰り | 未確認の一般化を避け、自分たちが解く課題として話す |

## Codexの活用と展開性

製品の中では、OpenAI Responses APIが会議とタスクを調整し、各PCのCodexが調査・実装を担当します。
作業Codexには議事録・元発言の検索手段がありますが、この試作生成で検索ツールが呼ばれたとは説明しません。

製品を作る開発では、本人が「触って修正を返す体験」を指定し、Codexでコードを調査して、当日のプレビュー・修正依頼・前後比較を実装しました。
9月15日09:41の `be57d37` と10:07の `1346767` が、この説明の具体的な根拠です。
Engine・Clientの事前開発と当日の変更を分け、T118の提出時の書面開示にも反映します。

まず届ける先は、Discordで共同制作する小規模なゲーム・アプリ開発チームです。
ゲームの移動比較と同じ流れを、UI案に実際に入力して比べる場面へ広げます。
導入にはEngine・Client、Codexの実行環境とモデル利用の設定が必要です。「誰でも無設定ですぐ使える」とは説明しません。
第三者の継続利用と会議時間の短縮は、今後測る項目です。
